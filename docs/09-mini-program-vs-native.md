# 09 · 微信小程序 vs 原生 iOS：可行性、工期与商业影响

- 文档版本：v1.0
- 日期：2026-10-22
- 状态：技术形态评估，不改变当前“原生 iOS”基线
- 关联：[README](../README.md) · [产品需求](01-product-requirements.md) · [技术架构](02-technical-architecture.md) · [开发计划](03-delivery-plan.md) · [中国上线合规](04-launch-compliance.md)

> **结论**：可以做一个小程序版本，但**不能简单认为“换成小程序就能明显缩短工期”**。只有在“云端一键处理、弱化实时精修、接受照片上传、放弃/重构 iOS 订阅”的前提下，小程序才可能更快；如果坚持本地实时形变、自然精修与月订阅，小程序不会明显更快，甚至更慢、更贵、更难变现。

---

## 1. 一句话判断

| 问题 | 判断 |
|---|---|
| 能否用小程序实现？ | **能实现轻量版/云端版**；完整本地实时人像精修不适合 |
| 是否明显缩短工期？ | **仅“云端一键版”可能缩短**；本地实时版不会 |
| 是否适合当前产品？ | **不建议把主产品直接改成小程序**；可作为获客/验证/轻量体验 |
| 最大硬伤 | **iOS 小程序数字订阅支付限制** + 照片上传/云端成本 + 实时形变性能 |
| 推荐路径 | 原生 iOS 主产品；小程序做“轻修/预约/风格测试”获客，或先用小程序云端版验证需求 |

---

## 2. 小程序能做什么、不能做什么

### 2.1 能做的

- 微信登录（`wx.login` → openid/unionid），比自建账号简单。
- 相册选图、拍照、图片压缩、保存到相册、分享给好友/群。
- Canvas 2D / WebGL 做基础滤镜、裁剪、简单磨皮、简单网格形变预览。
- 调用云端 API 做人脸/人体分割、形变、皮肤、物体擦除。
- 微信支付（Android 为主；iOS 数字内容支付受限制，见第 5 节）。
- 小程序备案、隐私协议、类目审核后上架。
- 社交裂变：分享、扫码、群聊、朋友圈广告落地页。

### 2.2 难做/不能做的

| 能力 | 小程序限制 | 影响 |
|---|---|---|
| 本地实时 12MP 形变 | Canvas/WebGL 性能、内存、纹理尺寸受限 | 预览需降分辨率；滑杆实时性差 |
| 端侧人脸/人体 ML | 小程序端侧模型能力/包体/性能有限 | 通常要云端，上传照片 |
| 高质量磨皮/去瑕疵 | 复杂滤波/局部修复在 JS/Canvas 上慢 | 需云端或降质 |
| 物体擦除 | 端侧生成式模型几乎不可行 | 必须云端 GPU，成本/隐私/审核 |
| 大图导出 | Canvas 尺寸/内存限制 | 需云端导出或分块，失败率高 |
| 订阅自动续费 | iOS 数字订阅支付受限；微信代扣有资质/类目要求 | 月付模式可能无法在 iOS 跑通 |
| 桌面图标/高频复访 | 小程序入口深、留存弱 | 不如原生 App 适合高频工具 |
| 复杂手势/性能调优 | 受 WebView/ Skyline/基础库版本影响 | QA 矩阵大，体验不一致 |

> 小程序不是“更轻的原生”，而是另一个运行环境；图像管线要重新实现，不能直接复用 Core Image/Vision/Metal。

## 3. 三种可行架构

### 方案 A：小程序 + 云端一键处理（最快，但产品变了）

```text
选图 → 上传 → 云端人脸/人体/皮肤/擦除
→ 返回成片 → 保存/分享
```

- **优点**：前端简单；算法可先用云端 API/开源模型；一套代码覆盖 iOS/Android；微信登录/分享天然。
- **缺点**：照片必须上传；延迟 2–10 秒/张；GPU/带宽成本；隐私/合规重构；订阅支付受限。
- **适合**：验证“用户要不要一键自然精修/擦除”，不是最终本地产品。
- **工期**：约 **12–18 周**（依赖第三方 API 与简化交互）。

### 方案 B：小程序本地 Canvas/WebGL + 轻量算法

```text
本地选图 → 降分辨率预览 → WebGL 滤镜/简单形变
→ 导出（可能仍需云端高清）
```

- **优点**：照片不上传；交互快；隐私好。
- **缺点**：形变/磨皮质量与性能受限；人脸/人体分割弱；大图导出难；开发/调优不比原生少。
- **适合**：轻量滤镜/模板，不适合“自然瘦脸瘦身 + 背景保护”。
- **工期**：约 **20–28 周**，且质量风险高。

### 方案 C：小程序获客 + 原生 App 履约（推荐，但两套）

```text
小程序：风格测试 / 一键预览 / 预约 / 分享
原生 App：完整精修、导出、订阅
```

- **优点**：小程序低门槛获客；原生保证质量/性能/订阅。
- **缺点**：两套产品/两套审核/两套数据；MVP 阶段成本高。
- **适合**：原生 App 上线并验证后，再做小程序获客。
- **工期**：原生 24 周 + 小程序 8–12 周（不含联动）。

## 4. 工期对比（关键）

| 路径 | 范围 | 预计工期 | 相对当前 24 周 |
|---|---|---|---|
| 原生 iOS（当前基线） | 本地实时形变/皮肤/风格/月订阅 | **24 周 / 250 PD** | 基准 |
| 小程序云端一键版 | 上传→云端处理→下载；弱交互 | **12–18 周** | 可能快 6–12 周，但产品/隐私/支付变了 |
| 小程序本地实时版 | Canvas/WebGL + 轻量算法 | **20–28 周** | 不明显，质量风险更高 |
| 小程序 + 原生双端 | 获客 + 履约 | **32–40 周** | 更慢、更贵 |
| 纯 H5/公众号 | 类似小程序但无微信原生能力 | 12–20 周 | 支付/留存更差 |

**为什么“看起来快”**：

- 省掉原生 iOS 的 Vision/Core Image/Metal 开发；
- 微信登录/分享/支付（Android）现成；
- 不需要 App Store 审核（但仍需小程序备案/类目审核）。

**为什么实际不一定快**：

- 图像算法要重写；云端 GPU/队列/审核/存储要新建；
- 大图上传/下载/失败重试/成本；
- iOS 订阅支付限制导致商业化返工；
- 小程序基础库/机型/Canvas 兼容测试并不少；
- 一旦要做“自然形变 + 背景保护”，云端模型调优和原生一样难。

## 5. 商业化：iOS 订阅是最大硬伤

你的方案是 **¥29.9/月订阅**。在小程序里：

- 微信支付在 Android 上可用，但**订阅自动续费**需要“委托代扣”能力，通常有主体/类目/资质要求。
- iOS 小程序内的数字内容/虚拟服务支付受微信与 Apple 规则严格限制；**不能像原生 App 一样接 StoreKit/IAP**。
- 可能出现：Android 能卖、iOS 不能卖；或只能单次购买、不能自动续费；或需要特殊类目/资质。
- 这不是“技术实现”问题，而是**商业模型是否成立**的问题；必须在立项前向微信开放平台/Apple 核实最新政策。

**结论**：如果月订阅是核心收入，**原生 iOS 更稳**；小程序更适合广告/线索/单次付费/引流，而不是数字订阅主阵地。

---

## 6. 合规与隐私

小程序不等于“免合规”：

- 需要**小程序备案**、主体资质、类目审核（图片处理/工具类）。
- 需要隐私保护指引、用户授权、照片上传/删除说明。
- 若云端处理人脸/身体，涉及敏感个人信息、PIPL、单独同意、数据本地化、内容审核。
- 若擦除构成生成式 AI，涉及生成式 AI/深度合成标识与安全评估。
- 微信审核对“美颜/瘦身/颜值”类内容可能更敏感；文案不能制造容貌焦虑。
- 照片上传后，“本地处理”信任优势消失；需要重新设计隐私叙事。

## 7. 体验与留存

| 维度 | 原生 iOS | 小程序 |
|---|---|---|
| 首次使用 | 需下载/信任 App | 扫码/搜索即用，门槛低 |
| 高频复访 | 桌面图标、通知、订阅 | 入口深、留存弱 |
| 性能 | Metal/Vision 原生 | Canvas/WebGL/云端，受限 |
| 大图/精细形变 | 强 | 弱/需云端 |
| 分享裂变 | 系统分享 | 微信分享/群/朋友圈更强 |
| 订阅管理 | StoreKit 成熟 | iOS 支付受限 |
| 隐私 | 可本地 | 云端方案需上传 |
| 审核 | App Store | 微信小程序审核/备案 |
| 迭代 | 发版审核 | 小程序审核，通常更快 |

**判断**：小程序适合“拉新/轻体验/分享”，原生适合“高频精修/订阅/性能”。你的产品是高频人像工具，主阵地仍应是原生。

## 8. 推荐决策

### 推荐：原生 iOS 主产品 + 小程序后置获客

1. **先按 24 周做原生 iOS MVP**：保证形变/肤色/性能/订阅。
2. **上线后做小程序“轻修/风格测试”**：不承载完整编辑，只做获客/预约/分享。
3. **不要在 MVP 同时做两端**：会从 24 周变成 32–40 周。

### 如果目标是“最快验证需求”

可以做 **小程序云端一键版**，但把它定义为**验证工具**，不是最终产品：

- 只做“上传 → 一键自然精修/擦除 → 下载”；
- 不做实时滑杆/本地形变；
- 不做 iOS 订阅，先用免费/单次/预约；
- 用 12–18 周验证“用户是否愿意用、是否愿意付费”；
- 验证后再决定是否做原生。

### 不建议

- 把“本地实时瘦脸瘦身 + 背景保护 + 月订阅”整体搬进小程序；
- 为了省 App Store 审核而选小程序，却忽略小程序备案/类目/支付限制；
- 同时做小程序和原生 MVP。

## 9. 如果选小程序，当前文档要改什么

| 文档 | 变化 |
|---|---|
| 01 产品需求 | 交互从滑杆实时改为“上传—等待—下载”；隐私从本地改为云端；订阅改为单次/广告/预约 |
| 02 技术架构 | 去掉 Vision/Metal/Core Image；改为小程序 Canvas/WebGL + 云端 GPU/对象存储/审核 |
| 03 开发计划 | 12–18 周云端版，或 20–28 周本地版；团队改为前端+云端算法 |
| 04 上线合规 | 小程序备案/类目/隐私/上传/生成式 AI；支付限制 |
| 05 风险 | 新增云端成本、审核、支付、隐私、留存风险 |
| 06/07 | 重写需求矩阵与 Backlog |

**不建议在未确认 iOS 支付路径前，把小程序作为主产品立项。**

---

## 10. 最终回答

1. **能实现吗？** 能实现“云端一键修图/擦除”的小程序；完整的本地实时人像精修不适合。
2. **能明显缩短工期吗？** 只有云端一键版可能从 24 周降到 12–18 周；本地实时版 20–28 周，不会明显更快；双端 32–40 周。
3. **建议？** 原生 iOS 做主产品；小程序作为获客/轻体验；如果只想快速验证，做云端小程序但不要把它当最终产品，也不要在 iOS 上押注订阅。
